## The name

In Abbott and Costello's routine, a man asks who is playing first base and never gets an answer he can use, because the first baseman is named Who. The second baseman is What. The third baseman is I Don't Know.

Ask a production system which person an API call was made for, and which piece of software made it, when an AI agent sat in between. The conversation is often the same. The site is organized around making those two answers, and a few more, survive from the place they are known to the place they are needed.

That is as far as the joke goes. The name and the four-cornered mark in the site’s icon are the only references to it; everything else uses the terms the specifications use, and [the roles](/concepts/#roles) are explained without it.

## What is covered

- **Lessons.** Six, in order, for a developer who has called APIs and has not read an OAuth specification.
- **Flows.** Each way an agent can obtain and present credentials, as a sequence diagram with the messages on the wire.
- **Deployments.** How the starting credential changes with where the agent runs.
- **Standards.** The RFCs, drafts and specifications involved, with status.

The scope is authentication and authorization. Prompt injection, model safety and data governance appear only where they change an authentication decision, which is more often than one would like.

## How to read it

The site is written at three depths, and each is a complete account at its own level.

**[The lessons](/learn/)** build one model in plain words, with one example. They leave things out on purpose: a lesson draws authorization code with PKCE in eight steps, and the flow page draws eleven. Where a lesson and a flow page differ in detail, the flow page is the fuller account.

**The flow pages, the [decision guide](/guide/) and the deployment pages** are for choosing and building. A flow page opens with what happens in a few parts and who has to do what, and a glossary term can be pressed for its definition. Those overviews restate the page and add no facts to it.

**The [standards tracker](/standards/)** is for looking things up, and for seeing how settled each piece is.

The design of the lessons follows what is known about learning from text and diagrams. A figure makes its point in the state it first shows and repeats every variation in a table, because most readers do not click. Steps are advanced by the reader, and nothing plays until the reader asks for it. Common mistakes are stated and corrected by name. Questions come with an explanation of why each answer is right or wrong. None of it has been tested with readers yet, and this page will say so until it has.

## How facts were checked

The standards in this area change monthly, and a reference that is confidently out of date is worse than none. This is how the content was verified in November 2026.

**Specifications read at source.** The MCP authorization specification and its extensions, the A2A specification, the AP2 specification, and the OAuth and WIMSE working group draft sources were read from their public repositories. Kubernetes feature stages were taken from the project's versioned feature list and documentation source. How AWS, Google Cloud, Microsoft Entra and GitHub Actions handle workload identity was read from each provider's own documentation. Examples on flow pages follow those documents.

**The lessons** restate the flow pages and the Concepts page in plain words, and were then read against the specifications they lean on: the OAuth framework and its security best current practice, the JWT profile for access tokens, token exchange, DPoP, the step-up challenge, the MCP authorization specification and the Kubernetes documentation. So were the page on hosted apps and the short answer on Kubernetes. The page on gateways was read against the MCP specification's authorization, security and transport pages; its table of products comes from each project's documentation. **The overviews** on flow pages were checked against the page each one opens.

**IETF revision numbers, dates and process states**, such as whether a draft is in last call or with the RFC Editor, were read from the IETF datatracker. The dates of RFCs, and the later RFCs that update them, were read from the RFC Editor.

**A state worded as *reported*** comes from a secondary source. Treat it as a prompt to check the linked source.

**Vendor products** are described from vendor documentation and announcements, and were not tested. That page says so at the top.

Every tracker entry links to its canonical source. If the two disagree, the source is right.

## How status is worded

<div class="table-scroll" tabindex="0" role="region" aria-label="Table: How status is worded">

| Label | Meaning |
| --- | --- |
| RFC | Published by the IETF. Stable, though possibly updated by later RFCs |
| Final spec | Approved as final by another body, or a released version of a protocol specification |
| WG draft | Adopted by a working group that intends to publish it. Can still change incompatibly |
| Individual draft | A proposal by its authors. No endorsement, and no guarantee it will progress |
| Project / platform | Open-source software or a platform API, not a specification |
| Guidance | A report, framework or best-practice document |

</div>

## How flows are rated

Each flow page carries a rating: stable, emerging or experimental. The rating describes what the flow depends on.

**What counts.** Each specification a flow page lists has one role.

<div class="table-scroll" tabindex="0" role="region" aria-label="Table: Roles of a reference">

| Role | Meaning |
| --- | --- |
| Required | The page names it as what the flow implements, a numbered step shows something it defines, the page teaches a security or validation rule it sets, or the page says a conforming implementation must support it, whether or not that path is drawn |
| Optional extension | Offered as a variant or an addition. No step depends on it, and nothing on the page requires it |
| Background | Named for context only |
| Not settled | The sources read so far do not decide which of these it is |

</div>

**How a required reference is judged.**

<div class="table-scroll" tabindex="0" role="region" aria-label="Table: Maturity levels">

| Level | Evidence |
| --- | --- |
| Stable | An RFC, or another body's final specification. For a project or a platform: its own statement of stability, such as a specification its maintainers mark stable or a feature documented as generally available |
| Emerging | A draft adopted by a working group. For a project or a platform: a feature its maintainers mark as beta or incubating |
| Experimental | An individual draft, a specification before its first stable release, or a feature marked alpha or experimental |

</div>

A mechanism is not experimental merely because no standards body owns it. It is judged on what its maintainers publish about its stability. Where that evidence has not been found, its level is recorded as unknown, not assumed.

The same holds in the other direction. Where a published specification says that one of its features may still change, a reference to that feature is judged on that statement, not on the publication. MCP’s URL-mode elicitation is in a published revision of the specification, which says its design may change in future revisions, so it counts as emerging.

**The rating.** A flow takes the level of its least mature required reference. One working-group draft among them makes the flow emerging; one individual draft makes it experimental. Optional extensions and background references never change it.

**When nothing is required.** A flow that requires none of its references has no level to take, and is shown as not rated. It is not called stable for having no draft among its references, and it is not rated from a product’s release stage. The [credential broker](/flows/credential-broker/) is the one such page today: no standard defines the pattern, the products that implement it differ, and no step depends on any one of them. How ready it is depends on the product you choose.

**When a role is not settled.** A reference whose role is not settled is not counted, and it is not assumed to be optional. If it is less mature than the flow's rating, or its level is unknown, requiring it would lower the rating. The rating is then provisional, and shown as such, until that reference is classified. If it could not lower the rating, the rating stands. No reviewed flow has an unsettled reference today, so none is provisional.

**What the rating is not.** It describes the dependencies of the arrangement the page draws. Where a page covers more than it draws, as the pages on workload identity federation, AAuth and agent payments do, it says so above the diagram and beside its required references: those references and the rating belong to the arrangement drawn, not to every implementation. The rating does not say the flow is secure, or ready for production where you run it. A stable flow can be deployed badly, and an emerging one can be the right choice.

**Coverage.** Every flow has been reviewed under this rule. In a review, each reference a flow lists is read and given a role: required, optional or background, or marked as not settled. Every flow’s page groups its references under those roles, and its rating is worked out from the required ones.

## Examples are illustrative

Hostnames, tokens and keys in examples are made up or taken from the specifications' own examples. Requests are abbreviated for reading. Do not copy an example as an implementation; follow the specification it illustrates.

## Corrections

If something here is wrong or out of date, [open an issue](https://github.com/kevinswiber/whosonfirst.ai/issues). Name the page, and link the source that disagrees with it.

The site is built from structured data: one file per flow, one list of standards, one glossary. A correction is usually a one-line change, so a pull request is welcome too. The repository says [how to make one](https://github.com/kevinswiber/whosonfirst.ai/blob/main/CONTRIBUTING.md).
