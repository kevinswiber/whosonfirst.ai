# Releasing guide search

Cloudflare Workers Builds publishes the guide. Every push to `main` starts the **Release guide search** workflow, which publishes the sibling search Worker once the site serves the same commit. Each static build writes `/search/release.json` with the public Git commit and SHA-256 digest of the passage manifest. A source archive without Git can build the site and has a null commit in this file. Production release requires both values.

## Set up once

The search Worker uses standard invocation telemetry. A search is `GET /search?q=…`, with the question in the query string. Both Workers set `observability.redactQueryString`, so logs and traces record the address without it, and the search Worker emits no application logs. Review account-level logging and retention separately.

1. Keep the primary site on Workers Builds with the production branch set to `main`. Set up the sibling Worker and its narrow same-origin route `whosonfirst.ai/search` separately in the Cloudflare zone. The route has no wildcard: it takes the search address and leaves `/search/`, the search page, and the files under it to the primary Worker, which handles every other page. Confirm the namespace binding points at the intended AI Search namespace and the instance has both keyword and vector indexing enabled.
2. In the public repository create the **search-production** GitHub environment, select `main` as its deployment branch, and use the repository’s existing review and CI policy. The release workflow uses the trusted code merged there. Its triggers are pushes to main and manual dispatches from main in the upstream repository.
3. Set the environment variable `SEARCH_RATE_NAMESPACE` to an operator-chosen numeric identifier dedicated to this Worker’s rate limiter. Use a different number from other limiters in the same account. The identifier is configuration and does not require another permission or a quota increase. Set it once and reuse it across releases. Optional environment variables are `SEARCH_WORKER_NAME` (default `whosonfirst-ai-search`), `SEARCH_NAMESPACE` (default `whosonfirst`), and `SEARCH_INSTANCE` (default `whosonfirst-guide`). Use the same values for indexing and retrieval.
4. Set the environment secret `SEARCH_RATE_LIMIT` to the number of searches one address may make in a minute. The limiter counts each Cloudflare location on its own, and its count is approximate. It is a secret, not a variable, so that the public run log masks it.
5. Set the search Worker’s secret `SEARCH_DAILY_BUDGET` to the number of searches that may reach AI Search in a UTC day: `npx cf workers secrets update SEARCH_DAILY_BUDGET --worker whosonfirst-ai-search`. One Durable Object, `SearchBudget`, counts them for every location. Once the day’s count reaches the budget, search answers that it has answered all it can for today, until midnight UTC. Quick matches still work, because they are a file. Without the secret, or with one that is not a whole number above zero, search is unavailable rather than unlimited. To change the budget, update the secret. The release keeps it.
6. Set environment secrets `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_AI_SEARCH_UPLOAD_TOKEN` and `CLOUDFLARE_SEARCH_WORKER_DEPLOY_TOKEN`. Scope both tokens to the intended account. The upload token needs AI Search Edit and Run, at the account level: it lists and uploads items and purges the instance’s cache. Grant the deployment identity the **Editor** role on the existing sibling Worker. It needs to upload a version and activate it on that Worker. Keep route-editing/DNS permissions out of both tokens. Each token is available only to its matching release step.
7. The first release with `SearchBudget` stops at `cf workers versions create`, which cannot create a Durable Object. Build the same commit of `main` with the production environment’s settings, run `npx cf deploy --prebuilt` once in `workers/search` with the deployment credentials, then run the workflow again on `main`. Later releases do not need this.
8. To release the current commit again after changing settings or credentials, choose **Actions → Release guide search → Run workflow** and select `main`.

## Pull request previews

Open the site preview linked by **Workers Builds** on the pull request. The site Worker’s existing Git connection runs `npx cf previews deploy` for non-production branches. The native preview build serves both the branch’s pages and `/search` at that URL. GitHub Actions tests the preview with local fixtures and needs no preview secrets.

Quick matches come from the branch’s catalog. Full search uses the published `whosonfirst-guide` index and accepts hits whose content keys match the branch’s rendered passages. Added or edited passages become eligible once the production release indexes them. The previews share a separate rate limiter. Its limit per address is the build variable `SEARCH_RATE_LIMIT` in the site Worker’s preview build settings, and a preview does not build without it. Previews count against the same daily budget as production, through the search Worker’s `SearchBudget`, because they spend the same queries. A preview reads its cap from the secret `SEARCH_DAILY_BUDGET` in the site Worker’s Previews Base. A Preview copies the Base secrets when it is created, and later changes to them reach only new Previews, so set the secret before a branch’s first push. A preview without it answers that search is unavailable until the secret is set on that Preview itself. Each Worker stops at its own cap on the shared count, so a preview cap below production’s leaves the rest of the day’s searches to production. Only the production release workflow uploads passages.

To check a branch locally, run `SEARCH_RATE_LIMIT=5 npm run search:preview:build`. The limit in this example is for a local build. It builds the same preview entrypoint and tests its search and page handlers. Run `npm run build` to return to the production site build.

## What a release does

The workflow builds the checked-out commit and the sibling Worker together. It validates the manifest locally, checks that the commit is still at the head of upstream main, then polls the live site's marker. After the local and live commit and manifest digest agree, `search:sync` uploads missing content-addressed items, reuses indexed items and waits for Cloudflare to report completion and at least one indexed chunk for every current passage. Then it purges the instance’s similarity cache, because new passages do not clear an answer cached from the earlier index. Item inventory, upload and purge errors stop the run before Worker activation.

The release helper rechecks main and the public marker, uploads a version with the pinned CLI's `cf workers versions create --prebuilt`, then rechecks again immediately before assigning 100% of the sibling Worker's traffic to that version with `cf workers deployments create`. These version and deployment commands do not manage zone routes. Each Worker version embeds the matching manifest and HTML form from the same build. A search that passes the limit for its address is counted against the daily budget before it reaches AI Search, and one that does not pass is not counted. Each search asks AI Search to reuse a cached answer only for a near-identical question (`super_strict_match`), whatever the instance’s own cache setting. With the looser default, a search for RFC 9396 listed a page that does not mention it (seen 21 November 2026). The response’s `Server-Timing` header gives how long the address limit, the budget and AI Search took, and nothing about the question. The service returns opaque keys.

Each question has one address. The Worker searches the question in a plain form: compatibility characters such as full-width digits become their plain form, and runs of spaces become one. The reader’s capitals are kept. Any other spelling of the address, including extra parameters, is redirected to it, and a search with no question goes to `/search/`. The search box asks for `&format=json` and the page without scripts for the HTML. [Workers Cache](https://developers.cloudflare.com/workers/cache/) keeps a found answer in front of the Worker for 48 hours (`s-maxage`), for each deployed version, so a release starts with an empty cache and nothing has to be purged. A cached answer does not run the Worker: it costs no AI Search query and is not counted against the limit for the address or the budget. On a cached answer, `Cf-Cache-Status` is `HIT`, and `Server-Timing` is the one the answer was found with. Every other response is `no-store`. A browser revalidates each answer (`max-age=0`). A link to a search can be followed from any site, but a request another site makes in the background is refused, and so is a browser opening a search ahead of time (`Sec-Purpose: prefetch`). The site’s speculation rules leave `/search` out, and `robots.txt` disallows it. Only keys in that embedded manifest can become results.

A final synthetic `GET /search?q=…&format=json` to the same-origin route checks that it serves the expected commit and digest and can return a passage. Workers Cache keeps answers for each version, so it is answered by the version just activated. It sends a fixed example question and prints only the outcome. A failed smoke test **after activation** means the new version might already be serving. Check Cloudflare deployment history and the route before retrying. To reproduce the build without credentials or a deployment, run `npm run build`, `npm run search:sync -- --dry-run`, then `SEARCH_RATE_NAMESPACE=1 SEARCH_RATE_LIMIT=5 npm run search:build`. The disposable local limiter ID and limit belong only in test builds.

## Review retrieval quality

Before enabling the release or promoting a change to passage extraction or ranking, run the editorial evaluation against the populated instance with the same build and manifest. `node scripts/evaluate-search.mjs --json > /tmp/guide-search-evaluation.json` submits the fixture questions in both keyword and hybrid modes, with AI Search’s cache off, and saves the displayed results. `node scripts/evaluate-search.mjs --replay /tmp/guide-search-evaluation.json --review` prints their destinations and excerpts, followed by the scores. Omit `--review` for just the scores. Use the account, instance and evaluation credentials named by that script. No reader queries are needed.

The fixed set contains 15 situations, five lookups, one ambiguous question and two off-topic controls. Where possible, repeat the comparison with unfamiliar readers’ questions that were reserved from ranking development. Compare situations with an intended destination in the first three, exact lookups with the intended destination first, ambiguous queries covering both interpretations in the first three, and off-topic questions returning no passages. Check whether the excerpt lets a reader distinguish the correct destination from a plausible neighboring flow. Record the fixture revision, scores and significant misses. Choose the hybrid rollout only when it improves situation retrieval while retaining dependable exact lookup and usable excerpts; report ambiguity and false positives explicitly. The automated release smoke measures availability and version agreement. Retrieval quality is decided by this review.

## Retries and rollback

Runs are serialized. If a new push supersedes a run, the older run fails its next main-commit check. Retry the run for current main. If the site build never appears, fix its deployment and rerun. A failed upload may leave built-in items or an inactive Worker version behind. Rerunning the current commit reuses its content-addressed items. A site deploy and a sibling activation are separate Cloudflare operations, so keep the marker and final smoke check in the release path.

For an incident, disable **Release guide search** in GitHub Actions and cancel any queued or in-progress release before making an independent rollback. In the sibling Worker's deployment history, identify the last healthy version by its **Guide search for** commit message. Redeploy that Worker version to 100% through the version/deployment controls. Retain its indexed passages and confirm links still exist on the live site. If destinations changed, roll the site and Worker back to their matching commit together. Confirm the public marker, search response headers and a real result, then re-enable the workflow and run it on `main` when the fix is in place. The zone route stays with its current owner.

## Retiring old passages

Ordinary sync preserves older built-in items. This permits fast rollbacks, but obsolete passages can occupy candidate slots before the Worker drops them. Keep the manifests from the current release and any Worker versions retained for rollback, or regenerate them from those commits and verify their revision digests. Before cleanup, enumerate candidate keys from manifests of releases actually uploaded by this project. Remove the union of all retained keys from that list and reconcile it against the instance's built-in item inventory. Review the resulting exact filenames and item IDs, including which releases used them. Delete only confirmed retired items by their item IDs. A filename pattern or the absence of a key from the current manifest alone is insufficient evidence of ownership. After cleanup, recheck retrieval; rolling back farther requires restoring the earlier manifest's items before activation.
