# AAuth review — 12 November 2026

## Scope and source authority

The existing AAuth flow follows one complete PS authorization exchange. Its glossary, guide, tracker and README descriptions use the same qualifications. This review establishes the guide’s source basis and teaching choices; it is not an implementation-conformance assessment.

The reference is [the author’s draft repository at e287b1e](https://github.com/dickhardt/AAuth/tree/e287b1e5d4616b61e5fcda1ac56b1be14f9d8d06). Its `draft-hardt-oauth-aauth-protocol.md` matches tag `draft-hardt-oauth-aauth-protocol-11`. The [Datatracker record](https://datatracker.ietf.org/doc/draft-hardt-oauth-aauth-protocol/) lists protocol -11 (25 September 2026), an individual Internet-Draft. HTTP Signature Keys is -09 (13 September 2026), also an individual Internet-Draft.

Supporting material, read without modification:

- [Protocol Explorer](https://github.com/aauth-dev/explorer/tree/e6d79137cda1a6a650d4394a37095393e1cc62ba), commit `e6d79137cda1a6a650d4394a37095393e1cc62ba`.
- [JavaScript packages](https://github.com/aauth-dev/packages-js/tree/9002b289db6fe9614831fe734d142c119139463b), commit `9002b289db6fe9614831fe734d142c119139463b`.
- The explorer’s `lib/scenarios/ps-asserted.json` understands person tokens but uses `EdDSA`, omits `alg` from the confirmation JWK, and adds `alg` to `Signature-Input`. Those conflict with protocol -11’s signature algorithm, common-claim and signing rules. This is specific evidence of drift, not a finding that every scenario is obsolete.
- The SDK’s `resource/src/verify-token.ts` requires an explicit accepted token-kind list, rejects `EdDSA`, checks `cnf.jwk`, audience and signature-key thumbprint. Its README depicts an older flow without the person-token step. Inspection does not establish complete SDK conformance; no SDK test suite was run.

The page links immutable source snapshots. GitHub citations use line anchors rather than the explicit heading IDs intended for the IETF renderer. The tracker’s OIDF migration claim is attributed to the author’s README, not presented as an IETF status change.

## Teaching and scenario decisions

Retain PS authorization rather than combine access modes. Alice is a returning calendar user, already bound to the agent at her PS, and has allowed this agent to act as her at this API. The API already maps her opaque `(iss, sub)` to the calendar account. This run obtains fresh `calendar.read` consent. The PS advertises no interaction relay endpoint, so the agent directs Alice to the interaction page itself. The alternatives note preserves the draft’s preference for relaying through the PS when available. No mission, AS, upstream API, sub-agent, account-linking flow or revocation exchange is drawn.

The protocol calls this three-party access because it counts agent, resource and PS. The diagram has five lanes because it also shows the person and provider. Enrollment is conceptual: the core draft does not specify one universal bootstrap exchange. Metadata retrieval is shown; repeated metadata/JWKS fetches used during token verification remain in the explanations, where their cache and trust roles can be explained.

Four preconditions appear once as a list before step 1. The four-token reference precedes the walkthrough. JWT examples explicitly separate header and payload as a decoded view, and HTTP token/signature strings are placeholders, not test vectors; all five signed-request listings include their signature headers. Both displayed content digests are computed from their exact bodies. The resource-token thumbprint is derived from the actual example public key. The diagram separates verification of the API challenge, user consent, verification of the returned grant, and the resource’s final enforcement.

Concrete corrections and qualifications:

- Replace an “eleventh revision” claim with the precise revision identifier -11.
- Avoid implying that every AAuth access mode requires a PS or a fresh user prompt.
- Separate provider enrollment from client registration at each resource.
- Show `typ`, issuer and confirmation key rather than teaching type checks with payload-only examples.
- State existing account mapping as a scenario assumption. Explain the draft’s new-record behavior on first contact, and label authenticated account linking as this guide’s recommendation. A valid foreign PS token cannot acquire Alice’s existing calendar by claiming the same name.
- Distinguish a resource token’s redemption lifetime from the resulting auth token lifetime.
- Explain that a purpose in `justification` does not narrow `calendar.read` to that purpose or time range.
- Explain the replay window and the lack of implicit query/body coverage.
- Do not imply that mission governance observes every API call, or that a chain necessarily narrows upstream permission.
- Describe the credential ledger as the credentials introduced in the walkthrough. Do not imply that unlisted servers lack issuer signing keys.
- Keep standards maturity experimental.
