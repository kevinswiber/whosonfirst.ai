## Teaching and scenario decisions

Retain PS authorization rather than combine access modes. Alice is a returning calendar user, already bound to the agent at her PS, and has allowed this agent to act as her at this API. The API already maps her opaque `(iss, sub)` to the calendar account. This run obtains fresh `calendar.read` consent. No mission, AS, upstream API, sub-agent, account-linking flow or revocation exchange is drawn.

The protocol calls this three-party access because it counts agent, resource and PS. The diagram has five lanes because it also shows the person and provider. Enrollment is conceptual: the core draft does not specify one universal bootstrap exchange. Metadata retrieval is shown; repeated metadata/JWKS fetches used during token verification remain in the explanations, where their cache and trust roles can be explained.

The four-token reference precedes the walkthrough. JWT examples explicitly separate header and payload as a decoded view, and HTTP token/signature strings are placeholders, not test vectors. The resource-token thumbprint is derived from the actual example public key. The diagram separates verification of the API challenge, user consent, verification of the returned grant, and the resource’s final enforcement.

Concrete corrections and qualifications:

- Replace an “eleventh revision” claim with the precise revision identifier -11.
- Avoid implying that every AAuth access mode requires a PS or a fresh user prompt.
- Separate provider enrollment from client registration at each resource.
- Show `typ`, issuer and confirmation key rather than teaching type checks with payload-only examples.
- State account mapping as an assumption. A valid foreign PS token cannot acquire Alice’s existing calendar by claiming the same name.
- Distinguish a resource token’s redemption lifetime from the resulting auth token lifetime.
- Explain that a purpose in `justification` does not narrow `calendar.read` to that purpose or time range.
- Explain the replay window and the lack of implicit query/body coverage.
- Do not imply that mission governance observes every API call, or that a chain necessarily narrows upstream permission.
- Describe the credential ledger as the credentials introduced in the walkthrough. Do not imply that unlisted servers lack issuer signing keys.
- Keep standards maturity experimental.
