# Implementation research, 14 November 2026

The first run of [implementation research](../implementation-research.md) across all 25 published flows. It started from `npm run implementations:coverage`, which counted 22 parties with no entry, 30 with one and nine flows with no deployment report. Six coding agents searched, one for each group of flows, and wrote a worksheet each per flow. Separate agents with no part in the search then read every accepted entry against its sources, as step 7 of the procedure asks, and corrected or excluded what the sources did not support. `npm run implementations:check` found every quoted passage on its page before anything was applied.

The run added 78 implementation entries and 15 deployment reports, and corrected three existing entries. It left 3 parties with no entry, 7 with one and eight flows with no deployment report. Ten parties were recorded as generic: they need nothing particular to their flow, and research does not look for them. No product was tested, no account was created and no protocol endpoint was called. These remain reviewed examples, not a census or a measure of use.

**Corrections to existing entries.** `identity-chain-authgent` and `txn-authgent` now follow authgent’s standards report, last updated 9 August 2026, which maps the code to revisions -17 and -11 and says a request naming a scope is refused when the subject token carries none. `oauth-mtls-kong` now says the plugin page marks it Enterprise only.

**Retrieval.** Uber’s engineering post answers HTTP 406 to the source command, so it has no recorded validator. It was read during the review. WSO2’s and NHS England’s documentation refused the request and their candidates wait for the next run.

Each flow below lists what was accepted, the leads held back only because a party already had enough entries, what was excluded and why, where the search looked, what it did not find and what the second reader changed.

### MCP authorization

- **Accept · MCP Python SDK, client OAuth provider and resource-server support.** On the server side, the SDK verifies bearer tokens through an application-supplied verifier, publishes RFC 9728 metadata and answers with a 401 that points to it. On the client side, it follows that pointer, discovers the authorization server and runs the code flow with PKCE, using a Client ID Metadata Document where the server advertises support. The application writes the token check itself and reports the token’s audience. The SDK refuses a token issued for another resource only when validate_token_resource is set, which is not yet the default. The client falls back to dynamic registration when the server does not advertise metadata documents. The SDK does not supply sign-in, consent or token issuance. [Authorization](https://py.sdk.modelcontextprotocol.io/run/authorization/) · [OAuth clients](https://py.sdk.modelcontextprotocol.io/client/oauth-clients/)
- **Accept · Codex, mCP client.** Documents OAuth for Streamable HTTP MCP servers, with Client ID Metadata Documents chosen when the authorization server advertises them and dynamic registration otherwise. It checks the returned issuer and can take scopes from the protected-resource metadata. The page does not name a target MCP revision. A pre-registered client ID skips registration. It does not establish behavior in every Codex surface or with every authorization server. [Model Context Protocol](https://learn.chatgpt.com/docs/extend/mcp)
- **Accept · Amazon Bedrock AgentCore Gateway, mCP gateway, resource-server side.** With JWT inbound authorization, the gateway checks tokens from a configured identity provider against an allowed audience, clients and scopes. A 401 or 403 carries a resource_metadata pointer to its protected-resource metadata. The identity provider is the authorization server. The guide warns that providers differ in whether they use the requested resource URL as the audience. IAM-based inbound authorization is a separate path. [Set up inbound authorization for your gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-inbound-auth.html)
- **Accept · Auth0 Auth for MCP, authorization server.** Issues tokens for MCP servers, supports resource identifiers and registers clients from Client ID Metadata Documents that an administrator enters. Registration by the client itself at runtime is a separate feature in Early Access. A tenant setting turns metadata-document registration on. Dynamic registration at runtime is in Early Access and not every tenant has it. The MCP server still publishes its own metadata and checks tokens. [Auth for MCP Is Now Generally Available](https://auth0.com/blog/auth0-auth-for-mcp-servers-generally-available/) · [Register Applications with CIMD](https://auth0.com/docs/get-started/auth0-overview/create-applications/register-applications-with-cimd)
- **Accept · GitHub, remote GitHub MCP Server.** GitHub announced its remote MCP server as generally available with OAuth sign-in, and its host guide describes protected-resource discovery from the 401 challenge. The guide follows the 2025-06-18 MCP revision and says dynamic client registration is not supported. Clients use a GitHub App or OAuth App. No count of users or sign-ins. [Remote GitHub MCP Server is now generally available](https://github.blog/changelog/2025-09-04-remote-github-mcp-server-is-now-generally-available/) · [GitHub Remote MCP Integration Guide for MCP Host Authors](https://github.com/github/github-mcp-server/blob/main/docs/host-integration.md)
- **Accept · Linear, linear hosted MCP server.** Linear documents OAuth 2.1 with dynamic client registration for interactive setup of its hosted MCP server, and read-only access through a read scope. Linear’s own documentation, undated. Bearer tokens and API keys are also accepted. It does not name an MCP revision. [MCP server](https://linear.app/docs/mcp)

### Credential injection at the egress proxy

- **Accept · Infisical Agent Vault, credential vault and egress proxy.** Infisical stores each service’s credential, host, and allowed methods and paths. A proxy outside the agent’s environment checks a time-bound session token, attaches the credential and forwards the request. The proxy can replace a placeholder in the path or query string as well as a header. A host no service covers is either forwarded without credentials or refused, depending on the proxy’s traffic policy. The session token is a bearer credential for the session’s lifetime. [How Agent Vault works](https://infisical.com/docs/documentation/platform/agent-vault/how-it-works) · [How Agent Vault works](https://infisical.com/docs/documentation/platform/agent-vault/how-it-works) · [How Agent Vault works](https://infisical.com/docs/documentation/platform/agent-vault/how-it-works) · [Agent Vault repository README](https://github.com/Infisical/agent-vault/blob/main/README.md)
- **Accept · Sprites Connectors, hosted credential store and API gateway.** Fly.io stores a credential for the organization and attaches it at a gateway URL that a Sprite sandbox calls without a token. An access policy, deny by default, decides which Sprites and which provider paths may use it, and expiring OAuth tokens are refreshed. The agent calls the gateway URL explicitly; this is not transparent interception of its outbound traffic. A custom connector can put the token in the query string or URL path. Calls must come from inside a running Sprite. [Connectors](https://docs.sprites.dev/concepts/connectors/) · [Connectors](https://docs.sprites.dev/concepts/connectors/) · [Hook your agent up to your APIs without handing it the keys](https://fly.io/connectors)
- **Exclude · Sandbox Runtime (srt), local sandbox egress proxy.** A valid lead, left out because the proxy party already has four entries, including a local host proxy (Docker Sandboxes), and this one fills no new party: the real values come from the host’s environment and files, not a vault. A later run can add it as the open-source local option. [Anthropic Sandbox Runtime README](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/README.md)
- **Accept · Fly.io, rails API calls to third-party OAuth APIs through Tokenizer.** Fly.io reports encrypting third-party API secrets to Tokenizer’s public key, so its Rails API holds only sealed secrets. Requests go through Tokenizer, which decrypts the secret, injects it and can restrict each secret to allowed hosts. The caller is Fly.io’s own application server, not an agent sandbox, and it carries the sealed secret in a request header rather than nothing. The 2023 post does not say the deployment is still running or how much traffic it carries. [Tokenized Tokens](https://fly.io/blog/tokenized-tokens/) · [Tokenized Tokens](https://fly.io/blog/tokenized-tokens/)
