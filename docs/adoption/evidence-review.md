# In the field evidence review

The initial source review was checked on **12 November 2026 (America/Los_Angeles)**. It covers five published flows and research for the planned AuthZEN flow. The first release’s [evidence records](../../src/data/field/records.ts) select 13 implementation entries and four operator accounts. Other published flows carry the state **Not reviewed**. Coding agents performed the source review and a separate check of the selected claims and publication rules; this record does not assert independent human or operator verification.

The review started with the [design and pilot findings](review-and-design.md), the pilot ledger and the site’s flow definitions. It opened product documentation, release announcements and first-party operator accounts. Targeted searches filled gaps in roles and operator evidence. The public selection is two or three actionable implementation entries and at most one operator account per flow. Further reviewed candidates and exclusions remain research context. The resulting records are examples. No new endpoint survey, operational test, independent certification or prevalence measurement took place.

Dates below identify a review, publication or reported event. A page’s update date applies to the document. An operator account can describe a rollout without establishing its date or current status. Adding an existing source to the directory is a change in evidence coverage. An unstated feature stage stays unspecified. Project and publisher wording is preserved at the scope it describes.

## Authorization code with PKCE

**Scope.** RFC 7636 with the OAuth authorization code grant, including S256 for the illustrated client. Generic OAuth, OIDC, or code grant support alone falls outside scope. Redirect variants, resource indicators and token audience each require their own evidence.

- **Accept · Amazon Cognito user pools, authorization server.** AWS documents a public app client using S256 and redeeming the code with the verifier. See _How Amazon Cognito uses PKCE_, steps 6–7. Stage and publication date unspecified. Support for the illustrated desktop callback, resource indicator and audience is outside this source’s claim. [Using PKCE in authorization code grants](https://docs.aws.amazon.com/cognito/latest/developerguide/using-pkce-in-authorization-code.html)
- **Accept · oauth4webapi, client library.** The project lists code flow with PKCE under _Features_ and v3.x under _Supported Versions_. The support statement applies to the library branch. Feature introduction and publication date are unstated. Native app integration and a specific issuer pairing remain untested. [oauth4webapi README](https://github.com/panva/oauth4webapi/blob/main/README.md#features)
- **Accept · GitHub OAuth Apps and GitHub Apps, authorization server.** The GitHub changelog labeled its S256 support announcement a release on 14 July 2025. The announcement describes verifier enforcement when the client sends a challenge and a historical compatibility exception. It covers user authorization for the named app types. [PKCE support for OAuth and GitHub App authentication](https://github.blog/changelog/2025-07-14-pkce-support-for-oauth-and-github-app-authentication/)

No qualifying operator account was selected. The GitHub announcement’s unnamed compatibility exceptions are rollout context. The pilot’s age-based inference of general availability was excluded.

## DPoP

**Scope.** RFC 9449 application-layer proof of possession for OAuth tokens. Client proof generation, issuer token binding and resource-server enforcement each need their own evidence. Certificate-bound access tokens, JWT client authentication and requirements in a specification are separate evidence.

- **Accept · Keycloak, authorization server.** The project moved DPoP from preview to supported in 26.4.0, released 30 September 2025. See _DPoP (supported)_ in the release announcement for public-client refresh-token binding, Keycloak endpoints and the option to require the authorization request thumbprint. A downstream API needs its own enforcement. [Keycloak 26.4.0 released](https://www.keycloak.org/2025/09/keycloak-2640-released)
- **Accept · oauth4webapi, client library.** The project’s `DPoP` API signs proofs with a supplied key pair and tracks server nonces. The README lists v3.x as supported. Feature introduction and publication date are unstated. The claim covers library functions. [DPoP API documentation](https://github.com/panva/oauth4webapi/blob/main/docs/README.md#dpop) · [oauth4webapi README](https://github.com/panva/oauth4webapi/blob/main/README.md#features)
- **Accept · Spring Security, servlet resource-server library.** The project’s `DPoPAuthenticationProvider` authenticates DPoP-bound access tokens on protected requests. The class documentation dates the API to version 6.5, and the checked servlet reference identifies 7.1.2 as stable. Publication date, original release day and issuer pairings are outside this claim. [DPoPAuthenticationProvider](https://docs.spring.io/spring-security/reference/api/java/org/springframework/security/oauth2/server/resource/authentication/DPoPAuthenticationProvider.html) · [OAuth 2.0 DPoP-bound Access Tokens](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/dpop-tokens.html)
- **Accept · Norsk helsenett, HelseID operator.** Its roadmap describes DPoP already in production. Under _Completed changes_, it dates proof enforcement for HelseID token calls to 1 June 2026. The roadmap’s publication date and the date of first production use are unstated. The downstream API milestones are separate. [HelseID planned changes](https://utviklerportal.nhn.no/informasjonstjenester/helseid/planlagde-endringar/vegkart/docs/planlagde_endringar_enmd)

Excluded from deployment evidence were the AT Protocol OAuth profile’s DPoP requirement and OpenID Foundation FAPI certifications. The certifications concern named versions and profiles. The pilot’s list totals do not establish general availability or deployment. [AT Protocol OAuth profile](https://atproto.com/specs/oauth) · [Certified FAPI 2.0 authorization servers](https://openid.net/certification/certified-fapi-2-0-op-security-profile-final-message-signing-final/)

## MCP authorization

**Scope.** OAuth authorization for remote HTTP MCP, using the site’s 2026-07-28 revision as the comparison point. Include documented discovery, client identity, resource-bound tokens and token verification tied to remote MCP. A role or component can be useful with partial support. Stdio credential handling and API-key-only access fall outside scope.

- **Accept · Claude Code, MCP client.** Anthropic documents protected-resource metadata discovery and use of a Client ID Metadata Document (CIMD). See _Use pre-configured OAuth credentials_ and _Override OAuth metadata discovery_. Stage, publication date and target MCP revision are unstated for these features. The claim applies to Claude Code. [Connect Claude Code to tools via MCP](https://code.claude.com/docs/en/mcp)
- **Accept · Workers OAuth Provider, authorization-server and resource-server library.** The README’s _Standards_ section references MCP authorization 2026-07-28. Its _Quick start_ shows CIMD and RFC 9728 discovery with resource-specific token checks. The application supplies sign-in, consent and policy. The documentation refers to 1.x without naming a stage or feature release date. The sample describes a library integration. [OAuth 2.1 Provider Framework for Cloudflare Workers](https://github.com/cloudflare/workers-oauth-provider)
- **Accept · Keycloak, authorization server.** The integration guide’s _MCP version compliance_ table marks the 2026-07-28 authorization-server support experimental. The preceding table documents separate flags for resource indicators and CIMD. The revision date belongs to the specification. The MCP resource server supplies protected-resource metadata and validates tokens. [Integrating with Model Context Protocol (MCP)](https://www.keycloak.org/securing-apps/mcp-authz-server)
- **Accept · Stripe, operator of its hosted MCP service.** Stripe’s _Manage MCP access and sessions_ section describes OAuth consent for live-mode accounts and sandboxes and links to the 2026-07-28 MCP specification. It gives no launch date. This is operator documentation for one hosted resource server. The review did not exercise the exchange or verify conformance. [Model Context Protocol (MCP)](https://docs.stripe.com/mcp)

No dated implementation change was selected. The pilot’s older or partial client entries and the CIMD directory need role-specific review before use. The attempted retrieval of Stripe’s live protected-resource metadata was unsuccessful. Stripe’s hosted-service claim rests on its product documentation. [Stripe’s protected-resource metadata URL](https://mcp.stripe.com/.well-known/oauth-protected-resource)

## Workload identity federation

**Scope.** A receiver trusts an identity established in another domain and issues short-lived access. Include runtime issuers, receiving token services and documented exchanges across CI, cloud, on-premises or SaaS boundaries. Same-domain native workload identity and user delegation fall outside scope.

- **Accept · GitHub Actions, workload identity issuer.** GitHub documents an OIDC JWT issued for a workflow job for presentation to a receiver with configured trust. See _Understanding the OIDC token_. Stage and publication date unspecified. The receiver’s credentials and configuration vary. [OpenID Connect](https://docs.github.com/en/actions/concepts/security/openid-connect#understanding-the-oidc-token)
- **Accept · Google Cloud IAM Workload Identity Federation, receiving token service.** See _Workload identity pool providers_ for Security Token Service exchange of external credentials under RFC 8693 and _Why Workload Identity Federation?_ for direct resource access or service account impersonation. Stage and publication date unspecified. The page displays 13 November 2026 UTC as its last update. [Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)
- **Accept · Pulumi, operator of its own CI and vendor of the broker.** In _Our approach_ and _Scale_, Pulumi describes GitHub Actions OIDC tokens exchanged for Pulumi Cloud tokens, followed by Pulumi ESC obtaining short-lived cloud credentials through its OIDC login providers. Pulumi published the account on 31 March 2026 and updated it on 16 June 2026. The rollout covered more than 70 Pulumi provider repositories, within one operator. Exact rollout dates and current operation remain unknown. [How We Eliminated Long-Lived CI Secrets Across 70+ Repos](https://www.pulumi.com/blog/eliminating-ci-secrets-with-pulumi-esc/)

Excluded were inferred GA and the conversion of a historical PyPI Trusted Publishers figure into an organization count. The OpenSSF guide, last updated May 2025, attributes a lower bound of more than 13,000 **projects** to an external chart. The pilot’s PyPI provider tabs are issuer options listed by one receiver. Indeed’s report also describes federation of SPIRE JWT identities with AWS and Confluent. Pulumi is the single selected federation report. [Trusted Publishers for All Package Repositories](https://repos.openssf.org/trusted-publishers-for-all-package-repositories) · [Indeed Engineering account](https://engineering.indeedblog.com/blog/2024/07/workload-identity-with-spire-oidc-for-k8s-istio/)

## SPIFFE identities and mutual TLS

**Scope.** SPIFFE X.509-SVID issuance, delivery and use for workload mutual TLS. A JWT-SVID or generic mTLS alone falls outside the illustrated path. Authorization policy is separate from peer identity.

- **Accept · SPIRE, identity issuer and local workload identity provider.** The project describes SPIRE as production-ready. See _SPIRE Architecture and Components_ and _A Day in the Life of an SVID_ for attestation, X.509-SVID issuance and delivery through the Workload API. Publication date unstated. Server and Agent are components of one product. An application or proxy still establishes mutual TLS. [SPIRE Concepts](https://spiffe.io/docs/latest/spire-about/spire-concepts/)
- **Accept · Istio with SPIRE, mesh integration.** The Istio guide’s introduction describes Envoy fetching SPIRE identities through SDS over a Unix socket. The documented setup uses a SPIFFE CSI driver and workload registration. Stage and publication date are unspecified for the integration, which relies on SPIRE for issuance. [SPIRE integration](https://istio.io/latest/docs/ops/integrations/spire/)
- **Accept · Indeed, operator.** In _SPIRE_ and _Istio Opinions_, Indeed Engineering reports using SPIRE in production for more than a year and using SPIRE-issued X.509 identities for mutual TLS in Istio. It published the report on 3 July 2024. This dates the report. Exact start and current operation remain unknown. Its fleet of 3,000 pods is deployment context. [Secure Workload Identity with SPIRE and OIDC: A Guide for Kubernetes and Istio Users](https://engineering.indeedblog.com/blog/2024/07/workload-identity-with-spire-oidc-for-k8s-istio/)

Ecosystem and adopter lists were excluded as deployment counts. Packaging SPIRE does not yield another independent issuer implementation. The SPIRE 1.16.0 change for infrastructure Agent SPIFFE ID paths was reviewed as a dated release candidate and left out of the selected events. The release notes flag a potentially breaking change for external plugins or custom Agent path templates. [SPIRE v1.16.0](https://github.com/spiffe/spire/releases/tag/v1.16.0)

## Stored observations

The first release publishes no observed-support records. The following pilot classifications were reviewed to retain the original units and delimit what a later observation could say. They refer to the files labeled 13 November 2026 UTC.

- In the pilot’s convenience panel, 69 of 82 organization entries were classified as advertising S256 and 7 of 82 as advertising DPoP algorithms. An entry was positive if any configured issuer matched. The stored rows contain organization-level flags. These are metadata classifications. Missing flags leave behavior unknown.
- The pilot selected 2,500 remote endpoints from a public MCP registry using a hostname-based operator heuristic. Of 2,463 HTTP responses to unauthenticated `initialize`, 931 returned 401. Of those 931, 818 had the pilot’s `resource_metadata` challenge signal and 835 yielded a document accepted by the collector’s permissive field check. The collector did not interpret response bodies for the 1,392 HTTP 200 and two HTTP 202 responses. These figures establish HTTP status and discovery classifications within that sample. The instrument cannot assess the site’s 2026-07-28 revision, which removed initialization. The 37 unanswered requests have unknown behavior.

The [pilot design review](review-and-design.md) records the collection and publication limits. The pilot artifacts are retained on the pilot branch.

### AuthZEN tool-call authorization

The proposal asks whether an authenticated agent may take a particular action on a particular resource. Its core is the Access Evaluation API in OpenID AuthZEN Authorization API 1.0, published as Final on 11 January 2026. A policy enforcement point (PEP) asks a policy decision point (PDP) for a decision. Application policy, identity mapping, and enforcement are additional responsibilities. MCP/COAZ binding support needs separate evidence. [Issue #72](https://github.com/kevinswiber/whosonfirst.ai/issues/72) · [Authorization API 1.0](https://openid.net/specs/authorization-api-1_0-final.html)

- **Accept for research · OpenFGA, PDP.** _Enabling AuthZEN_ and _Endpoints_ document opt-in experimental evaluation, batch evaluation, search and discovery endpoints. The product docs link the final AuthZEN 1.0 text. Product release date and minimum version are unspecified. Certification and tool-call deployment are unverified. [AuthZEN API (Experimental)](https://openfga.dev/docs/interacting/authzen)
- **Accept for research · Traefik Hub MCP Gateway, PEP.** In _Configuration Example_, its AuthZEN middleware matches `tools/call` for `transfer_funds` and maps the destination account argument into the AuthZEN resource ID for evaluation. It illustrates OpenFGA as the PDP. The guide names the COAZ mapping and AuthZEN-MCP binding without a draft number or release stage. The page was updated on 2 November 2026. [AuthZEN for MCP Gateway](https://doc.traefik.io/traefik-hub/mcp-gateway/guides/authzen-mcp)
- **Accept for research · Traefik Hub API Gateway, HTTP PEP.** The vendor’s HTTP middleware example maps a refund request into a single evaluation, with batch evaluation documented separately. This is a second product surface from the same vendor. The page was updated on 10 November 2026 and gives no stage or AuthZEN revision. [AuthZEN](https://doc.traefik.io/traefik-hub/api-gateway/reference/routing/http/middlewares/ref-authzen)

The reviewed sources contain no qualifying operator report for an AuthZEN-backed tool-call deployment. The working group’s interoperability results describe participation in draft scenarios 00–04. Some endpoints were hosted by third parties. Those results were excluded as production, release or final-profile certification evidence. Topaz’s draft-era announcement and the prospective Keycloak PDP announcement need current product release evidence. The agentgateway mock MCP example remains pending version-specific review. [OpenID AuthZEN Interop](https://authzen-interop.net/docs/intro/)
